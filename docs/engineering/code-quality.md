# 代码质量与维护规范

本文是本仓库所有后续代码的必遵循约定，与架构文档、工程验收标准共同生效。目标是让维护者能够找到入口、理解原因、局部修改并验证结果，而不是增加抽象层的数量。

## 1. 职责清晰与解耦

- 页面只编排组件、路由参数和页面级状态，不实现请求细节、正文解析或动画算法。
- 组件负责呈现和直接交互；composable 负责有生命周期的状态与行为；model 负责可独立调用的业务规则；repository 负责数据访问契约。
- UI 不直接依赖 mock 文件、localStorage、fetch 或后端响应格式，通过所属模块的服务访问数据。存储读写通过 shared/services/storage.js 处理版本、异常和回退。
- 纯函数不读取路由、DOM、store、当前时间或全局随机数。需要这些输入时显式传参；时间、随机源等在引擎边界提供默认值，测试时可替换。
- 组件数据向下通过 props，用户动作向上通过 emits；不修改 props、不调用子组件内部私有状态，不通过全局 DOM 查询寻找其他组件。
- provide/inject 仅用于明确的应用服务或组件作用域上下文，不作为隐藏的全局状态渠道；注入失败应给出可定位错误。
- 跨业务通过模块公开入口使用，禁止绕过 index.js（UI）或 services.js（应用服务）公开入口深层导入；禁止循环依赖和通用事件总线。
- 优先把状态放在使用它的最小作用域。只有确实跨页面共享的客户端状态才进入 Pinia。

## 2. 扩展方式

- 新增分类与话题从数据产生，不在多个组件里维护重复名单；分类展示顺序如需配置，放入文章模块配置。
- 新增饮料通过角色配置与绘制参数扩展，不复制完整角色组件；基础动作与腮红、爱心反馈独立。
- 修改烟花间隔、数量、尺寸和色彩范围，通过效果配置完成，不深入组件或逐帧函数修改魔法数字。
- 新增内容来源通过实现 repository adapter 接入，不修改页面请求逻辑。前端契约变化时同步修改 adapter、JSDoc 与使用方。
- 抽取公共能力之前先说明复用对象；仅一个场景的逻辑保留在所属模块。禁止为假想需求预建插件系统、万能组件或大量空接口。
- 配置只开放有实际用途的选项，写明默认值、单位、范围和互斥规则。不要把整个组件实现转换成难以理解的配置对象。
- 公共接口保持少量且稳定。修改 props、emits、repository 或持久化格式时明确兼容影响；存储升级必须有版本与失效策略。

## 3. 易读性与复杂度

- 名称说明具体含义：articleId、selectedCategory、launchIntervalMs；时间变量带单位，避免 duration 实际含义不明。
- 不使用 data1、temp、flag 等模糊名称；绘图中的 x/y、循环索引等局部数学变量可以使用简短名称。
- 优先具名函数、提前返回和清晰分支；不嵌套三元表达式，不用复杂布尔表达式混合请求、赋值和展示逻辑。
- 模板中只保留简单展示条件；筛选、排序、转换和组合规则放到 computed、composable 或纯函数中。
- 不为了减少行数压缩代码，不以链式操作隐藏副作用；异步流程统一使用 async/await，必须说明错误如何被消费。
- 单文件达到约 300 行、单函数达到约 50 行或分支嵌套超过 3 层时，触发职责检查，而不是机械拆分。像素图形数据可以独立成文件；合理保留需解释其内聚原因。
- 不保留注释掉的旧实现、未使用的导出、调试日志、无期限 TODO 或可有可无的兼容分支。
- 保留原始错误的 cause 或必要上下文，但不要将内部堆栈、凭据或用户评论写入生产日志。

## 4. 统一代码风格

由 Prettier 与 ESLint 自动执行，禁止开发者各自选择格式。脚手架阶段按下列规则落地配置。

| 项目              | 约定                                                                  |
| ----------------- | --------------------------------------------------------------------- |
| 缩进              | 2 空格，不使用 Tab                                                    |
| JavaScript 字符串 | 单引号；插值使用模板字符串                                            |
| 分号              | 保留                                                                  |
| 行宽              | Prettier printWidth 100，格式器负责折行                               |
| 尾逗号            | Prettier trailingComma all                                            |
| 相等与变量        | === / !==；默认 const，需要重新赋值才用 let；禁止 var                 |
| 模块              | ESM，业务函数优先具名导出；Vue SFC 与工具要求的配置默认导出除外       |
| 组件文件          | PascalCase.vue；模板组件使用 PascalCase                               |
| JS 文件           | kebab-case.js；composable 使用 use-xxx.js                             |
| 函数与变量        | camelCase；布尔量采用 is/has/can/should 等能表达判断的名称            |
| 模块常量          | UPPER_SNAKE_CASE；普通局部只读变量不强制大写                          |
| CSS 类名          | kebab-case；组件内 scoped；共享视觉值引用 tokens                      |
| imports           | 第三方 → 应用/模块公开入口 → shared → 同模块相对路径 → 样式，各组空行 |
| 路径              | 跨目录使用 @/ 别名；同目录可用 ./；避免多层 ../../                    |

Vue SFC 块顺序固定为 `<script setup>` → `<template>` → `<style scoped>`。script 内依次为 imports、props/emits、服务与状态、computed、行为函数、watch/生命周期。不是必须每类都存在，不添加空分组注释。

仓库说明和业务注释默认中文，标识符使用英文，品牌词、协议字段和专业术语保留原文。用户可见文案不得混入内部调试提示。

## 5. 注释要求

注释解释职责、规则和原因，不逐行翻译代码。修改行为时必须同步更新注释，错误的注释视为缺陷。

必须说明的地方：

1. 公共服务、业务纯函数、composable、引擎公开入口：JSDoc 描述用途、参数、返回值，以及有意义的错误或副作用。
2. 领域模型和外部边界：JSDoc typedef 说明字段含义、可空性、时间格式、状态枚举与单位；边界还需必要的运行时校验。
3. 非显然的业务规则：如返回位置优先级、活动聚合时区、点赞回滚、评论状态，解释为何这样处理。
4. 有生命周期的资源：解释谁创建、谁持有、何时释放；复杂并发与取消逻辑说明旧结果为什么必须丢弃。
5. 动效计算：说明坐标空间、单位、积分步长、随机采样时机与性能折中；角色轨道优先级必须清楚。
6. 兼容性修补：记录触发条件、采用原因和可移除条件；TODO 必须有具体待办及关闭条件或关联任务。

不要求每个内部小函数添加重复 JSDoc；不要给每个 ref、模板标签或 CSS 属性写显而易见的注释。ESLint 禁用应限制到最小作用域并写理由，禁止整文件随意关闭检查。

### 示例：公共配置

```js
/**
 * 数字烟花配置。时间统一使用毫秒；范围端点均包含。
 * 仅控制自动发射，手动触发不会重置已有烟花的生命周期。
 */
export const FIREWORKS_CONFIG = Object.freeze({
  launchIntervalMs: 5000,
  batchCount: Object.freeze({ min: 1, max: 5 }),
});
```

### 示例：解释状态边界

```js
// 爱心与腮红属于叠加反馈轨道；保持基础动作的时钟，避免点击打断喝芬达。
function handleMascotClick() {
  feedbackController.play('affection');
}
```

示例中的名称表达目标设计，不代表这些接口已经实现。

## 6. 数据、异常与安全

- 请求状态显式区分 loading、empty、error、success；写入操作区分 submitting，禁止拿空数组同时表达加载中和没有结果。
- 不静默 catch，不在失败时返回伪造成功；确实可忽略的异常记录原因并提供合理回退。
- 用户输入校验放在所属业务规则中，页面不复制校验条件；客户端校验不能替代服务端权限与校验。
- 评论文本不使用 v-html；正文渲染统一入口并处理不安全内容，禁止不同页面各自拼接 HTML。
- 快速筛选、切换文章和重复提交必须处理竞态；缓存按查询参数或 articleId 区分，不串文章状态。
- 禁止修改传入数组后排序、对外泄漏内部可变对象、在 computed 中写状态或发送请求。

## 7. 面向维护者的可发现性

每个业务模块第一次实现时增加简短 README，说明入口、职责、公开接口、状态来源及常见改动位置；小型 shared 工具不逐文件创建文档。

新增配置或业务功能时，同步维护 [常见修改入口](maintenance-guide.md)。说明必须对应真实存在的文件；尚未实现的条目明确标注为规划路径，不让维护者按不存在的入口操作。

复杂组件不依赖只能从运行结果猜到的参数。props/emits 接口先写语义，避免将内部变量整体透出给父组件。

## 8. 代码交付门槛

提交前检查：

- 文件是否放在正确模块，是否违反依赖方向或引入循环依赖。
- 改同一需求是否需要到多处同步常量；如需要，先解决事实来源重复。
- 公共接口、复杂规则和生命周期是否有准确注释。
- 交互是否处理失败、取消、重复和卸载场景。
- 是否通过现阶段实际可运行的 lint、format、typecheck、必要测试和构建。
- 是否更新对应维护说明，是否混入无关重构或调试代码。

自动检查覆盖格式、类型、依赖和部分行为；职责合理性、命名、注释质量与可读性仍需人工审查。文档约定在脚手架阶段落实为配置，不把“已写规范”表述为“检查已启用”。
